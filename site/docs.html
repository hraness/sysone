Sys1 documentation

Sys1 gives an agent or application one request format for yes/no, choice, and score decisions. Start with a local model, turn on hosted Jev when you want it, embed the router in a Bun app, or connect a compatible HTTP service.

Getting started

Pick the route that matches where your decision should run. Local Qwen is experimental; hosted Jev is opt-in and stays hosted-only when enabled.

Local, with Qwen

Install and select the experimental Qwen3 1.7B quality tier. The choice is persisted and is never silently replaced by a smaller installed model.

sys1 setup --tier quality
sys1 up
sys1 status

Hosted, with Jev

Set the credential in your environment, then enable Jev. Sys1 stores the activation flag, not the key, and a provider failure does not fall back to local inference.

export TYPESAFE_API_KEY=…
sys1 jev enable
sys1 up

Install the pinned release

Install the release file from GitHub when you want the CLI without building from source. --allow-scripts=node-llama-cpp lets only the native inference package run its install script.

npm install --global --allow-scripts=node-llama-cpp \
  https://github.com/hraness/sys1/releases/download/v0.11.0/hraness-sys1-0.11.0.tgz
sys1 doctor

Use sys1 setup --dry-run --json to inspect the local recommendation before downloading weights. Use sys1 doctor to inspect runtime, model store, routing, and daemon state.

Integration modes

The request and response contract stays the same while the lifecycle belongs to the mode you choose.

Portable client

Use the dependency-light @hraness/sys1/client entry from Node 24 or Bun. It validates requests, bounds response bodies, propagates cancellation, and makes one explicit HTTP attempt.

npm install --omit=optional \
  https://github.com/hraness/sys1/releases/download/v0.11.0/hraness-sys1-0.11.0.tgz

Loopback HTTP

Run sys1 up for a local daemon. The endpoint is POST /v1/systemone; discovery is GET /v1/models; liveness is GET /healthz.

Backends & models

Every backend accepts the same request and returns the same answer format. That says nothing about how well it answers, so keep the model identity and routing policy visible in your app.

Hosted Jev 1.13.0
TypeSafe’s hosted decision model. Enabling Jev selects hosted-only; the credential remains environment-only. Network-inclusive timing and provider capacity are outside local measurements.
Local Qwen3 1.7B
Selected by the quality setup tier and run through the pinned llama.cpp adapter. Local probability readout is experimental and must be evaluated on your own representative cases.
Local Qwen3 0.6B
Explicit compact diagnostic tier. It is not a memory-driven fallback and cannot silently replace the configured local model.
Local Qwen3.5 4B
Larger experimental model, a 2.55 GiB download. Install it with sys1 pull qwen3.5-4b; it answers only when you select it.
Compatible HTTP service
Register a service that implements POST /v1/systemone and GET /v1/models. Select it explicitly; adding a backend does not alter default routing.
Kev
Kev is a set of trainable decision models that runs as your own server. Register it with --adapter kev. Sys1 handles its required fields, two-decimal probability output, and structured score labels. You own the checkpoint, server, and any training.

Sys1 adapters return validated Jev-compatible answer shapes. They do not make generic local weights interchangeable with Jev, OpenJev, or another provider's calibration.

Profiles & tuning

Give each task a versioned set of questions and a model route. Reuse the same profile from application code or the CLI; each call supplies only the changing state.

const triage = createProfile({
  version: 1, id: "triage", revision: "1",
  model: "kev/kev-latest",
  questions: {
    urgent: { type: "noul", instructions: "Is there an active outage?" }
  }
});
const result = await client.evaluate(triage.request(ticket));

Import createProfile from @hraness/sys1/client. Save the definition as JSON for sys1 eval --profile triage.json, with {"state": ...} on stdin. Profiles also work with Jev and built-in local model routes.

Start by improving instructions and criteria against fixed application examples. If fine-tuning helps, train Kev separately, calibrate and evaluate the checkpoint, then publish a new profile revision pointing at its server. Profiles do not collect training data or start training jobs.
